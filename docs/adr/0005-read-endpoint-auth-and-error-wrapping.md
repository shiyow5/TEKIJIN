# ADR-0005: 読み取り系エンドポイントの認証方針と例外ラップ

- ステータス: 承認
- 日付: 2026-08-23
- 決定者: A チーム（プロトタイプ方針）

## 背景

PR #145 のレビュー（MEDIUM, #146）で、`GET /documents/{doc_id}` が任意 ID を無認証で
読め、`/ask` 等にある「予期しない例外 → `logger.exception` ＋汎用 500」のラップも無い、と
指摘された。ただしこれは本 PR 起因ではなく、読み取り系（`/documents`・`/inbox`・
`/questions`・`/dashboard`・`/employees`）全体の既存方針である。`/employees` の docstring にも
「プロトタイプに認証は無い」と明記されている。

決めるべきは2点:

1. 読み取り系のアクセス制御方針（社内文書の閲覧範囲を含む）。
2. 予期しない例外のラップ有無を、読み取り系で統一するか。

前提・制約:

- 本プロダクトは**プロトタイプ**であり、投入データは**すべて合成（デモ）**である
  （`fixtures/synthetic/`）。実在の個人情報・機密文書は含まない。
- 認証基盤（IdP・セッション・ロール）は未導入で、フロントは `/employees` の一覧から
  acting user を選ぶ（`asker_id` / 受信箱の responder id に流用）方式で動いている。

## 選択肢

- 案A: いま最小限の認証（APIキー／簡易セッション）を読み取り系に個別実装する。
- 案B: プロトタイプでは認証を入れず、**方針だけ決めて記録**し、認証導入時に読み取り系を
  **単一の依存性（access-control seam）**へ通す設計に寄せておく。例外ラップは今すぐ統一する。

## 決定

**案B を採用する。**

### 認証（方針の確定・実装は認証マイルストーンへ）

- プロトタイプでは読み取り系に認証を**入れない**。全データが合成であり、認証基盤も無いため、
  個別の場当たり認証はコストに見合わず、後で剥がす負債になる。
- 認証導入時は、読み取り系（documents/inbox/questions/dashboard/employees）を**単一の
  `require_reader` 依存性**（FastAPI `Depends`）へ通し、アクセス制御の判断を**1か所**に置く。
  各ハンドラに散らさない。
- **社内文書の閲覧範囲**（全社公開／部門限定／作成者限定 等）は**プロダクト判断が必要な
  未決事項**として残す。`require_reader` 導入時に、文書メタデータ（部門・機密区分）と
  acting user のロールで絞る前提で設計する。本 ADR ではその「置き場所（seam）」だけを固定する。

### 例外ラップ（今すぐ統一）

- 読み取り系すべてを、`routes.py` の `_generic_500(route)` コンテキストマネージャで包む。
  意図した `HTTPException`（404/422 等）はそのまま通し、それ以外の例外は
  `logger.exception` でスタックtrace を記録し、本文は汎用メッセージ（`内部エラーが
  発生しました`）の 500 に落とす。内部情報（例外メッセージ・接続先・スタック）を
  レスポンスに漏らさない。
- これで `/ask`・`/answer`・`/handoff`（従来からインラインで同等処理）と、読み取り系の
  ふるまいが**一致**する。

## 影響

- 読み取り系で予期しない例外が起きても、クライアントには一律で汎用 500 のみが返り、
  内部詳細はサーバログ（`logger.exception`）にだけ残る（情報漏洩の面が閉じる）。
- 認証は依然として無い（プロトタイプの明示的な受容）。**本番相当の公開前に**
  `require_reader` の実装と「社内文書の閲覧範囲」の確定が必須、という宿題が明文化された。
- 認証を1か所（`require_reader`）に集約する前提を先に決めたので、導入時に各ハンドラを
  個別に触らずに済む（seam が1つ）。
