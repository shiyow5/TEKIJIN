# ADR-0009: C6 の候補集合を全社員に広げても Hit@3 は上がらない（C4 の絞り込みは「事前分布」として効いている）

- ステータス: 承認
- 日付: 2026-08-26
- 決定者: A チーム（フルグラフ E2E 実測・3反復に基づく）
- 関連: ADR-0006（C6 証拠カバレッジ天井）/ ADR-0008（系統②の実 Hit@3 天井と算法レバーの負の結果）/ #87 / #100 / #158 / #405

## 背景

#87 は「C4（検索）で候補を絞ってから C6 に渡すと正解を落とす」と主張していた。根拠は、
証拠を持っているのに上位チャンクに現れなかった人が候補集合に入らない、という機構的な説明と、
当時のハーネス実測:

| 候補集合 | 層2 R@3（#87 起票時 / #158 後） |
|---|---|
| **全40名を C6 に渡す** | **0.771 / 0.727** |
| C4 相当の上位40名 | 0.741 / 0.707 |
| C4 相当の上位10名 | 0.729 / 0.679 |

実 DB（`research_e2e.py --task variants`）でも 0.753 → 0.775（+0.022）、
さらに #100 の時点では 0.732 → 0.836（+0.104）と報告されていた。

**ただしこれらはすべて `PipelineRanker` / 変種比較、つまり gold_topics を採点器へ直接与える
オラクル測定**である（ADR-0008 が指摘した乖離と同型）。

## 決定

**採用しない。`Settings.score_all_employees` は既定 False（＝C4 の候補集合）を維持する。**

### 実測（フルグラフ E2E・実 vLLM・全87行・**3反復のペア比較**）

`scripts/research_fullgraph_eval.py --question-fit --self-answer [--score-all-employees]`。
使い捨て DB（`eval87_tmp`）・CPU 埋め込み・製品既定（question_fit ON / self_answer ON）。

| 指標 | base（C4 の候補集合） | all（全社員） | 平均差 |
|---|---|---|---|
| **Hit@3** | **0.7778** [0.758 0.788 0.788] | 0.7626 [0.742 0.773 0.773] | **-0.0152** |
| Top1 | 0.6212 [0.621 0.621 0.621] | 0.6162 [0.606 0.606 0.636] | -0.0051 |
| Recall@3 | 0.6423 | 0.6372 | -0.0051 |
| MRR | 0.6944 | 0.6810 | -0.0135 |
| RouteAccuracy | 0.7546 [0.736 0.764 0.764] | 0.7639 [0.764 0.764 0.764] | +0.0093 |
| decision recall: **route（person）** | **1.000 ×3** | **1.000 ×3** | ±0 |
| decision recall: self_answer | 0.478 ×3 | 0.478 ×3 | ±0 |
| invoke 失敗行 | 0 ×3 | 0 ×3 | — |

- **3反復とも符号が同じ**で、Hit@3 の差は毎回きっかり 1 行分（1/66 = 0.0152）。
  LLM 非決定性（run 間 ±0.02）に埋もれる大きさではあるが、**改善方向の証拠はどの反復にも無い**。
- **person 経路 recall は 1.000 のまま**。実装が「スコアの候補集合だけを変え、C5 の経路シグナル
  （`route.py` の `if candidate_people:`）には触らない」設計になっていることが実測で確認できた。
- RouteAccuracy がわずかに動くのは、C6 が候補ゼロになる行が消えて `no_candidate` 終端に落ちなく
  なるため。person-gold の振り分け自体（decision recall の route クラス）は 1.000 で不変。

### なぜオラクル測定と食い違うのか

**C4 の候補集合は「絞り込み」であると同時に「その人が検索で引けた」という事前分布**でもある。
C6 のスコアはトピック一致が飽和しやすく（ADR-0006）、全社員に広げると
**「そのトピックの汎用スコアは高いが、この質問に関する証拠は無い人」が正解を押しのける**。
オラクル測定では C1 が常に正しいトピックを与えるためこの押しのけが起きにくく、
実グラフ（C1 トピック acc@1 が律速・ADR-0008）では顕在化する。

#405 の qsim（質問↔過去回答の意味一致）を既定 ON にしたことも効いている可能性が高い。
qsim は C4 の answer dense チャネル由来なので、**C4 に引っかからなかった人の qsim は定義上 0**。
候補だけ広げても、その人たちは質問特異的な加点を一切受けられない。

## 影響

- **`score_all_employees` は既定 False。** レバーは残す（`build_agent(score_all_employees=)` /
  `Settings` / `research_fullgraph_eval.py --score-all-employees`）ので、
  スコアラーやコーパスが変わったら 1 コマンドで測り直せる。
- **「C4 の候補生成をやめる」方向を、Hit@3 改善の手段として追わない。** #87 は本 ADR で close。
- ただし **#87 の「規模が大きくなったら」の指摘は生きている**: 数千人規模では全件スコアは重く、
  `person_topic_edges` からトピックで引く形が要る。それは性能の話であって精度の話ではない。
- 再測定手順:

  ```bash
  # DGX（共有機なので 1 構成ずつ・CPU 埋め込み・使い捨て DB）
  PYTHONPATH=backend/src CUDA_VISIBLE_DEVICES="" TEKIJIN_LLM_BACKEND=vllm \
    python scripts/research_fullgraph_eval.py --backend vllm \
    --question-fit --self-answer [--score-all-employees] \
    --db-url postgresql+psycopg://.../eval87_tmp --out fg87.json
  ```

  **1 回の run で判断しないこと。** Hit@3 は run 間で ±0.02 動く（ADR-0008）。
  最低 3 反復を base/all 交互に取り、符号が揃うかを見る。
