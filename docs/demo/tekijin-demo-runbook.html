Setup

共通セットアップ

管理者ログインで任意の asker_id になりすまし、トップから質問を投入 → 結果画面に「ルート（人／文書）」と推薦が出る。データはすべて合成（実在の個人ではない）。

判定の仕組み（一言用）

ルートは決定的ロジック。C4の3つのコサイン確信度で決める。文書を出すのは「文書類似度 ≥ 0.28 かつ 人適合 < 0.40」＝話題に強い文書があり人の適合が弱いとき。それ以外で候補者がいれば人に振る。恣意でなく信号ベース（ルート正解率 0.833・人recall 1.000）。

Demo 3 · Knowledge Loop

Slackで保存した知識が、次の質問で実際に出てくる

System3（蓄積）→ System1（自己回答）が繋がる瞬間。回答は知識ユニットから決定的に合成（LLM不使用＝ハルシネーションゼロ）、出典 ku_ 付き。

前提 有効化

TEKIJIN_KNOWLEDGE_RETRIEVAL_ENABLED=true floor 0.20 承認時に自動embed（#531 実装済み）

流れ デモ手順

  1. Slackのペアチャンネルで、回答者が具体的な打ち手を書いてから「解決しました」と送る。
    CRMは入力項目を最初の5つに絞り、日報と連携させると定着します。運用ルールを週次で見直すのが鍵です。
  2. bot が「残す／残さない」を出す → 残す → 下書き本文が表示される → 承認する（→ approved＋自動embed）。
  3. 実機で別の質問を投げる。
    CRMを導入したが現場が入力してくれません。定着させるコツはありますか。
  4. → 保存した知識が「システムの回答」として出る（出典 ku_xxx）。

証拠 本番E2Eの実出力

route/terminal : self_answered
grounded       : True
citations      : ['ku_2']
answer         :
  社内の類似ケースからの回答です。
  課題 : CRMを導入したが現場が入力せず定着しない
  打ち手: 入力項目を最初の5つに絞り、日報と連携させる。運用ルールを週次で見直す。
  結果 : 入力率が上がり定着した

見せ方

「さっき Slack で保存した知識が、別の人の次の質問で回答として出た。出典 ku_ 付きなので捏造でなく“保存した知識が根拠”」。

Reset

再実行とデータのリセット

デモ3は毎回新しい知識ユニット（source_id = slack_thread_<新thread>）を作る。溜まっても実害はないが、同じクエリで同じ結果を安定再現したいなら、デモ後に Slack由来の知識を消すと綺麗。
