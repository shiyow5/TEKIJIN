# TEKIJIN デモ・ランブック（実データ検証済み）

最終更新: 2026-08-27 ／ 対象環境: 本番DGX（フロント `http://internship-dgx1.tail349bcd.ts.net:13000`）

このドキュメントは、3つのデモを**実データで確実に動かす**ための手順・クエリ・裏付けをまとめたものです。
デモ1・2のクエリは本番グラフ（実vLLM＋実埋め込み＋本番DB）で route と top3 を検証済み。

## 0. 共通セットアップ

- **フロント**: `http://internship-dgx1.tail349bcd.ts.net:13000`（Tailscale）。管理者ログインで任意の `asker_id` になりすまして質問投入可。
- **質問の投げ方**: トップ画面から質問文を入力 → 送信 → 結果画面に「ルート（人／文書）」と推薦が出る。
- **話者データ**: 従業員40名・文書30本・スキル61・資格98・日報3070・案件120・過去QA151・従業員プロフィール40。すべて合成データ（実在の個人ではない）。
- **判定の仕組み（一言用）**: ルートは決定的ロジック `decide_route`。C4が出す3つの絶対コサイン確信度（回答/文書/人）で決める。
  - **文書を出す条件**: `文書類似度 ≥ 0.28 かつ 人適合 < 0.40`（＝話題に強い文書があり、人の適合が弱いとき）。
  - **人に振る**: 上記以外で候補者がいるとき（既定の着地点）。
  - 恣意でなく信号ベース。routed-set のルート正解率は実測 0.833、人recall 1.000。

## 🅰 デモ1：「文書を出すか・人を出すか」の選択を見せる

**狙い**: 同じ「詳しい方を探しています」調でも、システムがコーパスの信号で文書か人かを自動で選ぶことを示す。

### 使うクエリ（そのまま貼れる・実機検証済み）

| 順 | クエリ | 実機の判定 | 出るもの |
|---|---|---|---|
| ① 人 | システム開発・APIの件でご相談です。他社の仕組みとデータをやり取りする設計で迷っています。方針を相談したいです。 | **person** | 木村麻衣・佐々木隆・松本真理 |
| ② 文書 | 経理・決算の相談に乗ってもらえる方はいますか。月末の締め作業が毎回深夜までかかっているそうです。効率化の相談をしたいです。 | **document** | 経理・決算の手順書/チェックリスト/運用ガイド |
| ③ 文書 | 人事・採用について詳しい方を探しています。人が採れず、評価基準も曖昧で辞めてしまうそうです。制度から見直したいです。 | **document** | 人事・採用の運用ガイド/FAQ/提案テンプレート |

### 示し方
1. ①→②→③ を順に投入。結果画面の**「人カード」と「文書カード」が切り替わる**のを見せる。
2. 一言: 「文言はどれも“人を探す”口調。でも決算・採用は**整った手順書が既にある**のでシステムが文書を選び、API設計は**判断が要る**ので人を選ぶ。状況で出し分けている」。

## 🅲 デモ3：Slackで保存した知識が、次の質問で実際に出てくる

**System3（蓄積）→ System1（自己回答）が繋がる瞬間**を見せる。回答は知識ユニットから**決定的に合成**（LLM不使用＝ハルシネーションゼロ）、出典 `ku_` 付き。

### 前提（有効化）
1. `TEKIJIN_KNOWLEDGE_RETRIEVAL_ENABLED=true`（+ floor 0.20）。
2. 承認時に自動embed（#531 実装済み）→ 承認すれば即検索可能。

### デモの流れ
1. **Slackのペアチャンネル**で、回答者が**具体的な打ち手を書いてから**「解決しました」と送る。
   - 例（回答者）: 「CRMは入力項目を最初の5つに絞り、日報と連携させると定着します。運用ルールを週次で見直すのが鍵です。」
2. bot が「残す/残さない」を出す → **残す** → 下書き本文が表示される → **承認する**（→ approved＋自動embed）。
3. 実機で**別の質問**を投げる:
   - 「**CRMを導入したが現場が入力してくれません。定着させるコツはありますか。**」
4. → **保存した知識が“システムの回答”として出る**（出典 `ku_xxx`）。

### 検証済みの実出力（本番E2E）
```
route/terminal: self_answered   self_answer_grounded: True   citations: ['ku_2']
answer:
  社内の類似ケースからの回答です。
  課題: CRMを導入したが現場が入力せず定着しない
  打ち手: 入力項目を最初の5つに絞り、日報と連携させる。運用ルールを週次で見直す。
  結果: 入力率が上がり定着した
```

**示し方**: 「さっき Slack で保存した知識が、別の人の次の質問で回答として出た。出典 `ku_` 付きなので捏造でなく“保存した知識が根拠”」。

## 🔁 デモの再実行・データのリセット

デモ3は毎回**新しい知識ユニット**（`source_id = slack_thread_<新thread>`）を作る。溜まっても実害はないが、**同じクエリで同じ結果を安定再現**したいなら、デモ後に Slack由来の知識を消すと綺麗。

DGX上でのクリーンアップ（Slack由来の知識ユニットのみ削除）:
```bash
ssh team_a@100.118.131.67
cd /home/team_a/TEKIJIN/backend
env PYTHONPATH=src /home/team_a/tekijin-bench/.venv/bin/python -c "
from tekijin.data.db import get_engine
from sqlalchemy import text
with get_engine().begin() as c:
    n=c.execute(text(\"DELETE FROM knowledge_units WHERE source_type='slack_thread'\")).rowcount
    print('deleted', n)
"
```
> 注: これは knowledge_units のみ削除。Slackの会話・スレッド・承諾は消えない（必要なら別途）。
