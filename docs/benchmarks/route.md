# 経路判定 C5 の精度（Issue #88）

`eval_person.json` には全件に `gold_route`（`person` / `prior_answer` / `document` / `none`）が入っているが、
**測られていなかった**。C5（`backend/src/tekijin/agent/route.py`）の閾値もコード上
"All three are cosine-similarity constants, tunable on eval." と書かれたまま調整されていない。

実施 2026-08-22。C5 の `decide_route` を**そのまま import** し、C4 の3チャネルの絶対コサイン類似度を
埋め込みから再現して渡している（`answer_confidence` は retriever と同じく
「過去回答」と「回答のある過去質問」の近い方）。
再現: `python scripts/research_route.py --emb emb/emb_Nemotron-3-Embed-1B-BF16.npz`（**GPU不要**）。

## 1. 結論

**現在の閾値は一度も発火しない。全件が `person` になる。**

| | 全56件 | 自動ラベル25件（経路が散っている部分） |
|---|---|---|
| 経路の分布 | person 39 / document 10 / prior_answer 7 | person 8 / document 10 / prior_answer 7 |
| 多数決ベースライン | 0.696 | 0.400 |
| **現在の閾値 (0.80, 0.70, 0.50)** | **0.696**（＝多数決と同じ） | **0.320**（多数決を下回る） |
| 交差検証で調整した閾値 (0.55, 0.40, 0.40) | 0.750 | 0.440 |
| **トピックのコーパス状態から引く（LLM 予測トピック）** | — | **0.920** |

全56件で見ると「多数決と同点」に見えるが、これは人手ラベル21件の route を
`person` 固定で作っているせい（評価セット側の弱点。#84）。
**経路が実際に散っている自動ラベル25件で見ると、現在の閾値は多数決すら下回る。**

## 2. なぜ発火しないのか — 閾値が別の埋め込みモデル向けに較正されている

C5 の docstring はこう書いている。

> a near-duplicate is ~0.85-0.95, strongly related ~0.75-0.85, topically related ~0.6-0.75, weak <0.5

実際に Nemotron-3-Embed-1B で測ると、コサインの分布はまったく別の帯にある。

| チャネル | 最小 | 25% | 中央 | 75% | 最大 | 閾値 |
|---|---|---|---|---|---|---|
| `answer_confidence` | 0.12 | 0.21 | 0.24 | 0.31 | **0.54** | 0.80 |
| `document_confidence` | 0.04 | 0.12 | 0.16 | 0.20 | **0.57** | 0.70 |
| `people_confidence` | 0.08 | 0.21 | 0.27 | 0.32 | **0.45** | 0.50 |

**最大値ですら閾値に届かない。** `prior_answer` と `document` は構造上どのクエリでも選ばれない。

docstring の帯は e5 / BERT 系のコサイン分布を前提にしている。**コサインの絶対値はモデル依存**なので、
埋め込みモデルを変えるたびに較正し直す必要がある。#63（埋め込みの差し替え）とセットで見るべき。

調整後 (0.55, 0.40, 0.40) でも、`document` を10件中3件しか拾えず `prior_answer` は0件のまま。

```
gold＼予測          person  prior_answer  document
person                  39             0         0
prior_answer             7             0         0
document                 7             0         3
```

## 3. 経路はコサイン類似度ではなく、トピックのコーパス状態で決まる

評価セットの `gold_route` は `build_eval_v2.route_for()` が
**トピックごとのコーパス統計**（そのトピックの文書数・過去回答の平均 reuse）から決めている。

```python
if not experts:                                          return "none"
if p["docs"] >= DOC_THRESHOLD and p["mean_reuse"] < LOW_REUSE:  return "document"
if p["docs"] == 0 and p["mean_reuse"] >= HIGH_REUSE:            return "prior_answer"
return "person"
```

同じ規則をトピックから引くと、自動ラベル25件で

- gold トピックから引く: **1.000**
- **LLM 予測トピックから引く: 0.920**

**この 1.000 はラベルの作り方をなぞっているので、手法の強さの証拠ではない。**
ただし含意は残る: 「このトピックに社内文書が何本あるか」「過去回答がどれだけ再利用されているか」は
**コーパスについての事実**であって、クエリとチャンクのコサインで近似すべきものではない。

「文書に格下げすべきか」を決めたいなら、**そのトピックに手順書があるかを数えればよい**。
「過去回答で足りるか」を決めたいなら、**そのトピックの過去回答の再利用実績を見ればよい**。
コサインは「クエリが文書に似ているか」しか答えられない。

## 4. 提案

1. **閾値をこのモデルで較正し直す**（応急処置）。ただし調整後でも 0.440 止まり
2. **C5 をトピックのコーパス状態から決める形に変える**（本筋）。
   C1 がトピックを当てた後に、そのトピックの `documents` 件数と `answers.reuse_count` を引く。
   どちらも決定的な集計で、LLM も埋め込みも要らない
3. コサイン閾値は**残すとしても補助**に留める。近似重複の検出（`prior_answer`）だけは
   コサインのほうが素直なので、較正し直したうえで併用する

## 5. 限界

- **`gold_route` はコーパス統計の規則で作ったラベル**なので、§3 の比較は循環している。
  「経路の正解とは何か」を人手で決め直さないと、この構図からは出られない
- **人手ラベル由来の21件は route を `person` 固定**で作っている（評価セット側の弱点、#84）。
  そのぶん全56件での数字は `person` に有利に出る
- `answer_confidence` は「過去回答」と「回答のある過去質問」の最大で再現したが、
  製品の C4 は RRF 融合後の順位も持っている。**C5 が見ているのは絶対コサインだけ**なので
  ここは一致しているはず

個別値は `ablation/route_results.json`。
