# 充足判定 C2 の精度（Issue #111）

> ⛔ **この文書の結論は取り下げた。測り方が製品と違っていた（#113 / PR #112 の Codex レビュー）。**
> 正しい測定は **[llm_faithful.md](llm_faithful.md)** にある。
>
> 何が違ったか:
>
> * C1 に**検索結果8断片を見せていた**。製品では C1/C2 は C3/C4 の**前**に走り、質問文しか見ない
> * リクエストを手で写していたため、**`temperature=0.7`**（`ChatOpenAI` の既定値）と
>   C1 human の依頼者欄を落とし、JSON スキーマも Field description の無い手書きだった
> * 異常系20件を**全部 C2 の担当として数えていた**。`out_of_scope` / `adversarial` / `pii` は
>   `graph._after_c1` で C1 が弾く段で、**C2 に届かない**。`no_expert` は C6 の
>   `no_candidate` の担当で、下の表が期待値 `false` としているのも誤り
> * 正常系のラベルは `eval_person.json` の**検索用**であって充足ラベルではない
>
> 測り直した結論は逆だった: 同じ入力に対して**リポジトリ既定の決定的実装（stub）の方が厳しく**、
> 24件中0件しか通さない。**「聞き返しすぎ」は vLLM 固有の欠陥ではない。**
> ただし原因は経路ごとに別である — `_REQUIRED_SLOTS` を読むのは `RuleSufficiencyModel` だけで、
> `VllmSufficiencyModel.check` は LLM を直接呼ぶ。**vLLM 側で効きうるのはプロンプトの方**であって、
> `_REQUIRED_SLOTS` を緩めても vLLM の挙動は変わらない。
>
> 下の記述は**測定手順の記録として残す**。数値は使わないこと。

C2（`backend/src/tekijin/llm/vllm.py` の `VllmSufficiencyModel`）は、相談文だけで
「取り次げるか／聞き返すか」を決める段。**ここが厳しすぎると、答えられる相談まで聞き返しで止まる。**

モデル選定（[README.md](README.md)）では C2 正解率 **0.900** と載っているが、これは
`scripts/bench_llm.py` が **20件**（`insufficient` 5件 + L1/L2 から 15件）で測ったもので、
異常系は `insufficient` しか見ておらず、**C1 のトピックも渡していない**。
契約（`docs/specs/model-definition.md` §2 C2）では C2 は C1 の出力を受け取るので、その条件で測り直した。

実施 2026-08-23。実機 `internship-dgx1`、Qwen3.6-35B-A3B-NVFP4 + 構造化出力（guided JSON）。

## 1. 何を測ったか

| 群 | n | 期待する `sufficient` | 出どころ |
|---|---|---|---|
| 正常系 | 56 | `true` | `eval_person.json` の層2採点対象（L4 と gold 空を除く） |
| 異常系 | 20 | `false` | `eval_robustness.json`（`insufficient` / `out_of_scope` / `pii` / `no_expert` / `adversarial`） |

C2 には **相談文 + C1 が実際に出したトピック**（`llm_topic_ctx.json`）を渡している。

system プロンプトは2版を比較した。**変えたのは system だけで、渡す情報は両版とも同じ。**

- **`product`** … 製品の `_SUFFICIENCY_SYSTEM` をそのまま写したもの。**出荷時の挙動はこちら。**
  > あなたは情報充足の点検器です。取り次ぐ前に判断へ必要な情報が揃っているかを確認し、足りなければ『まとめて1つ』の逆質問を返します。
- **`scoped`** … 「何が揃っていれば十分か」を書き足した版。
  製品版は判断基準を書いていないので、モデルが自前の基準（部署名・予算・技術スタック…）を持ち込む余地がある。
  そこを「困りごとの対象・領域が特定できるか」に限定した。

**測っていないこと**: 製品の human 側は `トピック=… 製品=… 種別=…` という書式で、
`products` と `question_type` も渡す。本ハーネスの入力にはこの2つが無いので、
**字面を揃えるより情報量を揃える方を採り、両版とも「相談文 + C1 のトピック」で統一した**
（欠けている2つを既定値で埋めると、実際には 技術相談 の相談へ `種別=製品QA` と嘘を渡すことになる）。
温度0で1回ずつ、モデルは Qwen3.6-35B-A3B-NVFP4 のみ。

## 2. 結果 — 製品プロンプトは正常系を1件も通さない

| クラス | n | 期待 | **`product`（出荷時）** | `scoped` |
|---|---|---|---|---|
| 正常系（通常の相談） | 56 | `true` | **0/56 = 0.000** | **47/56 = 0.839** |
| `insufficient` | 5 | `false` | 5/5 = 1.000 | 5/5 = 1.000 |
| `out_of_scope` | 5 | `false` | 5/5 = 1.000 | 5/5 = 1.000 |
| `pii` | 4 | `false` | 4/4 = 1.000 | 4/4 = 1.000 |
| `no_expert` | 3 | `false` | 3/3 = 1.000 | 3/3 = 1.000 |
| `adversarial` | 3 | `false` | 3/3 = 1.000 | 3/3 = 1.000 |
| **全体** | **76** | | **20/76 = 0.263** | **67/76 = 0.882** |

**異常系はどちらも 20/20 で満点。差は正常系にしか出ていない。**
つまり `scoped` は「守りを緩めて通した」のではなく、**要らない聞き返しだけを減らしている。**

`product` が止めた56件のうち **51件では C1 が正解トピックを出せていた**（46件は第1候補で的中）。
C2 は、**次の段が既に答えを持っている相談を、質問で押し返している。**

グラフ側の `MAX_FOLLOWUPS = 1`（`agent/stubs.py`）があるので無限ループにはならない。
聞き返しは1回で打ち切られ、2周目は `capped` で強制的に `sufficient=True` になる。
被害は「止まる」ではなく **「全相談が必ず1往復ぶん遅れる」**。デモでは全問が質問返しから始まる。

### 応答時間も基準を割る

| | `product` | `scoped` |
|---|---|---|
| 出力トークン中央 | 131 | **26** |
| C2 p50 | 1.79s | **0.41s** |
| C2 p95 | 2.73s | **0.99s** |
| **C1+C2 p95**（C1 は 0.61s。合格ライン **3秒**） | **3.34s ✗** | **1.60s ✓** |

聞き返し文と `missing` を毎回生成するぶん出力が5倍になり、**単体で合格ラインを割る。**
`README.md` に載っている「C1+C2 合計 p95: 1.31秒」は旧ベンチ（n=20、C1 のトピックを渡さない）
での値で、**この条件では再現しない。**

## 3. 誤検出の中身 — 「分からないから聞く」ではなく「分かっているのに聞く」

`scoped` 版が聞き返しで止めた正常系9件は、**すべて L2(7) / L3(2)**。
L1（トピック語が明示されている易しい層）では1件も起きていない。
つまり C2 は「症状だけで書かれた相談」を落としている。**それは実運用でユーザーが書く形そのもの**である。

決定的なのは、**この9件のうち6件で C1 は正解トピックを出せていた**（うち5件は第1候補で的中）ことだ。

| id | 難易度 | C1 と gold の一致 | C2 が要求した不足 |
|---|---|---|---|
| p12 | L2 | 第2候補が正解 | 対象システム/業務内容、現在の技術スタック、予算/規模感 |
| p29 | L2 | **第1候補が正解** | 相談者の所属部署、具体的な相談内容 |
| p31 | L2 | C1 も外している | 具体的な業務内容、対象システム/ツール |
| p33 | L2 | 評価セット側に gold トピックが無い | 具体的な相談内容、対象部署 |
| p35 | L2 | 評価セット側に gold トピックが無い | 具体的な相談内容、対象部署 |
| p39 | L2 | **第1候補が正解** | 部署名、担当者名 |
| p41 | L2 | **第1候補が正解** | 具体的な業務内容（SNS運用、広告、PRなど）、予算規模、期間 |
| p51 | L3 | **第1候補が正解** | 設備名、基盤名、移管対象 |
| p56 | L3 | **第1候補が正解** | 対象システム、技術スタック |

いちばん分かりやすいのが **p41**。

> 相談文: 自社の発信そのものを外に任せたいと言われました。引き受けた経験のある方を探しています。
> C1 のトピック: **SNS運用**（正解） / Webマーケティング・広告 / 広報・PR
> C2 の聞き返し: 「自社の発信」が具体的に**SNS、Webサイト、プレスリリース**などのどの媒体や業務を指しているか、また予算感や期間について詳細を教えていただけますか？

**C2 は、C1 が既に順位づけした選択肢を、そのままユーザーに選ばせようとしている。**
`p39` の「部署名、担当者名」に至っては、**それを探すのがこの製品の役目**であって、
相談者が知っていたら相談しに来ない。

不足として挙がった語を並べると、`予算/規模感` `期間` `技術スタック` `担当者名` のように、
**取り次ぎ先を決めるのに要らない情報**が多い。C2 が見立てているのは「相談を受理できるか」ではなく
「見積もりを書けるか」に近い。判断基準を書いていない system プロンプトに対して、
モデルが SIer の一般的な要件ヒアリング項目を持ち込んでいる、と読める。

なお p33 / p35 は評価セット側の `gold_topics` が空の4件（eval id 32〜35、人手ラベル由来）に当たる。
**この2件については C2 が聞き返すのは妥当**とも言えるので、実質の誤検出は7件と見るのが公平。

## 4. 出力の形式は両版とも問題ない

| | `product` | `scoped` |
|---|---|---|
| JSON 妥当 | 76/76 | 76/76 |
| 聞き返し文の整合違反（`sufficient=false` なのに空文 / `true` なのに聞き返しあり） | 0件 | 0件 |

構造化出力（guided JSON）を使っている限り**形式面は落ちない**。
`SufficiencySchema` の `_followup_required_when_insufficient` バリデータが弾く形も1件も出ていない。
**C2 の課題は判断基準だけ**で、スキーマでもモデルでもデコード設定でもない。

## 5. 何をすべきか

**1. `_SUFFICIENCY_SYSTEM` に判断基準を書く（必須・小さい）。**
「情報が揃っているか」だけだと、モデルは SIer の要件ヒアリング項目（予算・期間・技術スタック）を
自前で持ち込む。C2 が決めるのは見積もりの可否ではなく **取り次ぎの可否**だと明示する。
本ハーネスの `scoped` 文面がそのまま使える（`scripts/research_llm.py` の `C2_SYS_SCOPED`）。

**2. C1 のトピックが取れているなら、そもそも聞き返さない。**
`product` で止めた56件の91%、`scoped` で止めた9件の67%で、C1 は正解トピックを出していた。
`intent.topics` が空でなく `intent.confidence` が閾値以上なら `sufficient=True` に倒す
ガードを C2 ノード側に置けば、プロンプトの機嫌に関係なく効く。
`RuleSufficiencyModel`（stub）は既にこの形（`intent.confidence < 閾値 or not intent.topics` のときだけ聞く）
になっている。**vLLM 版だけがこの安全弁を持っていない。**

**3. 「不足」の語彙を取り次ぎに要るものへ絞る。**
`部署名` `担当者名` を聞くのは、**それを探すのがこの製品の役目**である以上、筋が悪い。

**4. 回帰を止める。**
`docs/benchmarks/ablation/payload_c2.json` と本スクリプトで再測できる。
プロンプトを触るたびに正常系の通過率を見る。

## 6. 再現

```bash
# 入力を作る（GPU不要）
python scripts/research_payloads.py --task c2 \
    --topics docs/benchmarks/ablation/llm_topic_ctx.json \
    --out docs/benchmarks/ablation/payload_c2.json

# 実行（要 vLLM。--c2-prompt で system プロンプトを切り替える）
python scripts/research_llm.py --task c2 --c2-prompt product \
    --payload payload_c2.json --out c2_qwen36_product.json
python scripts/research_llm.py --task c2 --c2-prompt scoped \
    --payload payload_c2.json --out c2_qwen36_scoped.json

# 集計（GPU不要）
python scripts/research_c2.py \
    --result docs/benchmarks/ablation/c2_qwen36_scoped.json \
    --payload docs/benchmarks/ablation/payload_c2.json
```

生の出力は `docs/benchmarks/ablation/c2_qwen36_{product,scoped}.json`、
入力は `docs/benchmarks/ablation/payload_c2.json`。
