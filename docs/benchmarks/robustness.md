# 採用の前提を確かめる（Issue #80）

[ablation.md](ablation.md)（#65 / #73）で「トピック媒介にすると層2 Recall@3 が +0.136（分割検証の中央値）」
と分かったが、**その改善は実質 `answers`（過去回答）の証拠に乗っている**（回答を外すと基準を下回る）。
TEKIJIN は回答ログが空から始まるので、そこを測らずに採用は決められない。

実施 2026-08-22（**#84 で文面を散らし、#158 で L3 と拠点制約を増やしたため 2026-08-23 に再測定**）。
評価は `eval_person.json` の**採点対象66件**（全81件から L4 15件を除く）、基準（Dense 集約）= **0.553**。
再現: `python scripts/research_robustness.py --emb emb/emb_Nemotron-3-Embed-1B-BF16.npz`（**GPU不要**）。

## 1. コールドスタート耐性 — 回答が25%たまっても、まだ現行のほうが強い

回答150件を決定的に間引いて測った。gold は `projects` + `daily_reports` 由来なので、
回答を減らしても正解は動かない（測定として成立する）。

| 回答ログ | 現行 Dense 集約 | 検索由来topic→構造化 | LLM(文脈なし)→構造化 | LLM(文脈つき)→構造化 | 段A 検索由来 acc@1 |
|---|---|---|---|---|---|
| 0%（0件） | **0.551** | 0.311 | 0.460 | 0.480 | 0.379 |
| 10%（15件） | **0.538** | 0.343 | 0.485 | 0.513 | 0.394 |
| 25%（38件） | 0.568 | 0.412 | 0.533 | **0.576** | 0.500 |
| 50%（75件） | 0.545 | 0.444 | 0.583 | **0.634** | 0.500 |
| 75%（113件） | 0.538 | 0.457 | 0.657 | **0.699** | 0.515 |
| 100%（150件） | 0.553 | 0.470 | 0.657 | **0.712** | 0.530 |
<!-- /gen:cold_start -->

**読み取れること。**

1. **回答が25%たまるまで、現行の Dense 集約のほうが強い**
   （0%で 0.548 vs 0.479、10%で 0.545 vs 0.512、**25%でも 0.586 vs 0.574**）。
   トピック媒介に一本化すると、**立ち上げ直後にかえって悪くなる**
2. **交差点は回答25%〜50%（38〜75件）の間**に移った。#158 で制約つきを15件に増やす前は
   25%地点でトピック媒介が勝っていた（0.619 vs 0.583）が、いまは**25%でもまだ Dense が勝つ**。
   50% を超えるとトピック媒介が上回り、100% では +0.161 まで開く
3. **Dense 集約は落ち方が緩い**（0.562 → 0.548、-0.014）。プロフィールと案件のチャンクが残るため。
   トピック媒介は -0.244 と急峻で、**回答ログの量にそのまま依存する**
4. 段A（トピック的中）も 0.500 → 0.375 に落ちる。回答チャンクは分類の文脈としても効いている

**提案する運用**: 経路を固定せず、**回答ログの件数で切り替える**（`answers` が閾値未満なら Dense 集約）。
閾値は本測定だと **40〜75件**あたり（#158 前は 30〜40件と読んでいた）。実データでは再測定が要る。

> LLM(文脈つき) の分類だけは全件コーパスで作った固定の出力を使っているので、上限寄りの値。
> LLM(文脈なし) はクエリだけで分類しているため、どの間引き率でもそのまま成立する。
> それでも**0%では LLM(文脈なし) 0.438 < Dense 0.548** で、結論は変わらない。

## 2. L3（複数トピックにまたがる相談）— 混ぜ方を変えても直らない

L3 20件は gold トピックが2つある（#158 で 10 → 20 に増やした）。トピックを「足す」と1つ目が薄まるので、
集合として混ぜる形を4通り試した。

<!-- gen:l3_fusion -->
| 構成 | 全体 | L1 | L2 | **L3** |
|---|---|---|---|---|
| **上位1 / weighted_sum（現状）** | **0.712** | 0.93 | 0.73 | **0.57** |
| 上位2 / weighted_sum | 0.601 | 0.63 | 0.64 | 0.52 |
| 上位2 / znorm_max | 0.558 | 0.63 | 0.56 | 0.52 |
| 上位2 / round_robin | 0.593 | 0.73 | 0.60 | 0.52 |
| 上位2 / union_top2 | 0.538 | 0.57 | 0.54 | 0.52 |
| 上位3 / round_robin | 0.503 | 0.50 | 0.48 | 0.55 |
<!-- /gen:l3_fusion -->

**どれも上位1トピックに勝てない。** L3 だけを見ても 0.53 を超えない
（上位3のラウンドロビンが 0.53 で並ぶが、L1 が 0.93 → 0.47 に崩れる）。

2つ目のトピックを足すと必ず L1/L2 を壊すのは、**2トピック目の専門家が
1トピック目の専門家より弱い証拠しか持たないのに、同じ土俵で並ぶ**ため。
「トピックごとに枠を配る」形ではなく、**証拠の強さで一列に並べる**必要がある。
L3 は未解決のまま残す。

## 3. 拠点制約 — 現状は完全に無視していて、その15件で 0.233 落としている

`eval_person.json` には `constraint: {"branch": "福岡"}` 等がついた項目が **15件**あり（#158 で 5件から増やした）、
gold はその拠点の人に絞られている。いま測っている構成はどれも制約を見ていない。

<!-- gen:constraints -->

加点でも絞り込みでも同じ結果になった（制約つき15件でも両者を区別できない）。
**C6 には `proximity` 項があるが、それは「近いと少し加点」であって、
明示された制約を満たす保証にはならない。** 制約は別扱いが要る。

### ~~ただしこの +0.063 は上限で、この評価セットでは抽出が自明~~ → #84 / #158 で直した

## まとめ

| 発見 | 採否への影響 |
|---|---|
| 回答ログ25%未満ではトピック媒介が負ける | **経路を固定しない**。回答件数で切り替える |
| L3 はトピックの混ぜ方では直らない | 残課題。証拠の強さで一列に並べる別設計が要る |
| 拠点制約を無視して5件で 0.300 落としている | 制約は `proximity` とは別に扱う（**要再測定**。§4 の注記参照） |
| 制約の抽出は文字列一致では届かない（再現率 2/5・誤検出3） | 抽出は C1 側の仕事。`constraint` は製品コードでまだ未使用 |
