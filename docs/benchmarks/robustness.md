# 採用の前提を確かめる（Issue #80）

[ablation.md](ablation.md)（#65 / #73）で「トピック媒介にすると層2 Recall@3 が +0.130（分割検証）」
と分かったが、**その改善は実質 `answers`（過去回答）の証拠に乗っている**（回答を外すと基準を下回る）。
TEKIJIN は回答ログが空から始まるので、そこを測らずに採用は決められない。

実施 2026-08-22（**#84 で評価クエリ8件の文面を変えたため 2026-08-23 に再測定**）。
評価は `eval_person.json` の56件（#73）、基準（Dense 集約）= **0.592**。
再現: `python scripts/research_robustness.py --emb emb/emb_Nemotron-3-Embed-1B-BF16.npz`（**GPU不要**）。

## 1. コールドスタート耐性 — 回答が25%たまるまでは現行のほうが強い

回答150件を決定的に間引いて測った。gold は `projects` + `daily_reports` 由来なので、
回答を減らしても正解は動かない（測定として成立する）。

| 回答ログ | 現行 Dense 集約 | 検索由来topic→構造化 | LLM(文脈なし)→構造化 | LLM(文脈つき)→構造化 | 段A 検索由来 acc@1 |
|---|---|---|---|---|---|
| 0%（0件） | **0.560** | 0.354 | 0.458 | 0.509 | 0.393 |
| 10%（15件） | **0.551** | 0.378 | 0.482 | 0.545 | 0.411 |
| 25%（38件） | 0.583 | 0.446 | 0.545 | **0.619** | 0.482 |
| 50%（75件） | 0.583 | 0.527 | 0.610 | **0.688** | 0.518 |
| 75%（113件） | 0.586 | 0.551 | 0.682 | **0.753** | 0.554 |
| 100%（150件） | 0.592 | 0.551 | 0.682 | **0.759** | 0.554 |

**読み取れること。**

1. **回答ログが1割以下の間は、現行の Dense 集約のほうが強い**（0%で 0.560 vs 0.509、10%で 0.551 vs 0.545）。
   トピック媒介に一本化すると、**立ち上げ直後にかえって悪くなる**
2. **交差点は回答25%（約38件）あたり**。そこを超えるとトピック媒介が上回り、
   100% では +0.167 まで開く
3. **Dense 集約は落ち方が緩い**（0.592 → 0.560、-0.032）。プロフィールと案件のチャンクが残るため。
   トピック媒介は -0.250 と急峻で、**回答ログの量にそのまま依存する**
4. 段A（トピック的中）も 0.554 → 0.393 に落ちる。回答チャンクは分類の文脈としても効いている

**提案する運用**: 経路を固定せず、**回答ログの件数で切り替える**（`answers` が閾値未満なら Dense 集約）。
閾値は本測定だと 30〜40件あたり。実データでは再測定が要る。

> LLM(文脈つき) の分類だけは全件コーパスで作った固定の出力を使っているので、上限寄りの値。
> LLM(文脈なし) はクエリだけで分類しているため、どの間引き率でもそのまま成立する。
> それでも**0%では LLM(文脈なし) 0.458 < Dense 0.560** で、結論は変わらない。

## 2. L3（複数トピックにまたがる相談）— 混ぜ方を変えても直らない

L3 10件は gold トピックが2つある。トピックを「足す」と1つ目が薄まるので、
集合として混ぜる形を4通り試した。

| 構成 | 全体 | L1 | L2 | **L3** |
|---|---|---|---|---|
| **上位1 / weighted_sum（現状）** | **0.759** | 0.93 | 0.77 | **0.53** |
| 上位2 / weighted_sum | 0.652 | 0.57 | 0.75 | 0.40 |
| 上位2 / znorm_max | 0.586 | 0.57 | 0.63 | 0.43 |
| 上位2 / round_robin | 0.652 | 0.70 | 0.69 | 0.47 |
| 上位2 / union_top2 | 0.598 | 0.53 | 0.66 | 0.43 |
| 上位3 / round_robin | 0.515 | 0.47 | 0.52 | 0.53 |

**どれも上位1トピックに勝てない。** L3 だけを見ても 0.53 を超えない
（上位3のラウンドロビンが 0.53 で並ぶが、L1 が 0.93 → 0.47 に崩れる）。

2つ目のトピックを足すと必ず L1/L2 を壊すのは、**2トピック目の専門家が
1トピック目の専門家より弱い証拠しか持たないのに、同じ土俵で並ぶ**ため。
「トピックごとに枠を配る」形ではなく、**証拠の強さで一列に並べる**必要がある。
L3 は未解決のまま残す。

## 3. 拠点制約 — 現状は完全に無視していて、その5件で 0.300 落としている

`eval_person.json` には `constraint: {"branch": "福岡"}` 等がついた項目が5件あり、
gold はその拠点の人に絞られている。いま測っている構成はどれも制約を見ていない。

| 構成 | 制約つき5件 | 全体 | Δ（基準比） | 95%CI |
|---|---|---|---|---|
| 制約を無視（現状） | 0.700 | 0.759 | +0.167 | [+0.065,+0.265] |
| **拠点一致を加点**（RRF 重み0.5） | **1.000** | **0.786** | **+0.193** | [+0.092,+0.295] |
| 拠点で絞ってから並べる | 1.000 | 0.786 | +0.193 | [+0.092,+0.295] |

加点でも絞り込みでも同じ結果になった（この規模では両者を区別できない）。
**C6 には `proximity` 項があるが、それは「近いと少し加点」であって、
明示された制約を満たす保証にはならない。** 制約は別扱いが要る。

### ~~ただしこの +0.027 は上限で、この評価セットでは抽出が自明~~ → #84 で直した

**旧状態**: 制約つき5件が**すべて同じ文型**（`…できれば{拠点}の拠点で動ける方だと助かります。`）
で終わっていたため、拠点名の単純な文字列一致で **5/5 正しく取れ、制約なし51件での誤検出は 0** だった。
**これは抽出が簡単だという証拠ではなく、評価セットが定型的すぎただけ**である。

**#84 で制約の書かれ方を散らした**（id・gold ラベル・難易度の内訳は変えていないので、
採点対象56件という基準は動かない）。

| id | 制約 | 書かれ方 |
|---|---|---|
| 11 | 福岡 | 地域名から解決（「九州のお客様先に出向く…現地で動ける方」）。**拠点名を含まない** |
| 12 | 本社 | 制約を文頭に置く（「本社側で一緒に動いてくれる人を探しています」） |
| 13 | 本社 | **「本部」と言い換え**。拠点名とは文字列一致しない |
| 14 | 大阪 | 地域名から解決（「関西で対応できる方」）。**拠点名を含まない** |
| 15 | 本社 | 拠点名は出すが理由つきで、末尾定型ではない |

あわせて**制約に見えて制約でない**文を3件仕込んだ（`constraint` は `null` のまま。誤検出の検出用）。

| id | 文面 | なぜ制約でないか |
|---|---|---|
| 16 | 「大阪の事例があれば参考にしたい」 | 参照先であって担当者の拠点ではない |
| 18 | 「名古屋のお客様の件ですが、対応いただく方の拠点は問いません」 | 顧客所在地。**明示的に問わないと言っている** |
| 21 | 「東京で実施した施策の資料があれば見たい」 | 事例であって担当者の拠点ではない |

## 4. 制約の抽出しやすさ（#84 で追加）

`research_robustness.py` の §4 が毎回この場で測る。素朴な抽出＝拠点名がそのまま
書かれていたら拾う、というだけのもの。

| 評価セット | 再現率 | 誤検出（制約なし51件中） |
|---|---|---|
| 旧（定型） | 5/5 | 0 |
| **新（#84）** | **2/5** | **3** |

取り逃すのは id 11（福岡）・13（本社）・14（大阪）、誤検出するのは id 16・18・21 で、
**いずれも設計どおり**。これで「拠点名の文字列一致では届かない」ことが数字で言えるようになった。

> ✅ **文面を変えた8件を再埋め込みして測り直した（2026-08-23）。**
> **§3 の絶対値（制約つき5件 0.700 / 1.000、全体 0.759 / 0.786）は1桁も動かなかった。**
> 動いたのは基準線と、そこから引く Δ・区間だけ（**#84 の生成器修正後は 0.592**）。§1 の Dense 列も同様に動いた。
> 再埋め込みはクエリ71件だけを差し替える `scripts/research_reembed_queries.py` で行い、
> **文面を変えていない63件は旧埋め込みと cos 0.99994 以上**（中央値 1.000000）であることを確認した。

## まとめ

| 発見 | 採否への影響 |
|---|---|
| 回答ログ25%未満ではトピック媒介が負ける | **経路を固定しない**。回答件数で切り替える |
| L3 はトピックの混ぜ方では直らない | 残課題。証拠の強さで一列に並べる別設計が要る |
| 拠点制約を無視して5件で 0.300 落としている | 制約は `proximity` とは別に扱う（**要再測定**。§4 の注記参照） |
| 制約の抽出は文字列一致では届かない（再現率 2/5・誤検出3） | 抽出は C1 側の仕事。`constraint` は製品コードでまだ未使用 |
