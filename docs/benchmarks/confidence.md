# 確信度ラベルの較正（Issue #110）

> ⚠️ **「高」の方が「中」より当たらない。** 高 74.6% < 中 90.0%（差 **−0.154**、95%CI [−0.269, −0.037]、
> P(高>中) = **0.003**）。「低」は一度も出ない。
> 原因は、ラベルが見ている2つの素性が**どちらも当たり外れと無関係**だから。

`confidence_label`（`backend/src/tekijin/scorer/features.py`）はこう決めている。

```python
if edge_weight >= 0.7 and evidence_count >= 3: return "高"
if edge_weight >= 0.4 or evidence_count >= 2:  return "中"
return "低"
```

実施 2026-08-23。gold トピックを渡し、候補を全社員にして（#87）3枠 × 採点対象52件 = **156スロット**。
`scripts/research_e2e.py --task misrec` が1スロットずつ素性を残す。**GPU も検索も使わない**
（`rank(q, all_ids, …)` は埋め込みに依存しない）。

## 1. いま見ている素性は、当たり外れを見分けられない

| 素性 | AUC |
|---|---|
| `topic_fit`（= `edge_weight`） | **0.501** |
| `evidence_count` | **0.476**（0.5 を下回る＝**多いほど外れる**） |
| 合成スコア | 0.503 |
| **順位** | **0.647** |
| 次点とのスコア差 | 0.442 |

AUC 0.5 は「無意味」。**ラベルが見ている2つは、どちらも無意味かむしろ逆である。**

理由ははっきりしている。`edge_weight = 1 − exp(−Σ 証拠スコア)` は**すぐ飽和する**。
156スロット中 **113が 0.90 以上、60が 0.99 以上**で、閾値 0.7 は事実上「証拠が3件あるか」と同義になる。

そして証拠は**多いほど当たらない**。

| 証拠数 | 1 | 2 | 3 | 4 | 6 | 8 | 9 |
|---|---|---|---|---|---|---|---|
| 正解率 | 0.933 | 0.867 | 0.727 | 0.657 | 0.714 | 0.750 | 0.571 |
| n | 15 | 15 | 22 | 35 | 14 | 12 | 14 |

**「高」は `evidence_count >= 3` を要求するので、いちばん精度の低い帯を選んで「高」と呼んでいる。**

## 2. 効くのは証拠の「量」ではなく「種類」

| 証拠の種類 | あり | なし |
|---|---|---|
| `answer`（過去に答えている） | **0.820**（n=128） | 0.571（n=28） |
| `self`（本人申告のスキル） | **0.913**（n=23） | 0.752（n=133） |
| `cert`（資格） | 0.846（n=39） | 0.752（n=117） |
| **`project`（案件に参加）** | **0.677**（n=99） | **0.947**（n=57） |

**案件参加は負の証拠である。** 1つの案件に何人も乗るので、
「そのトピックの案件にいた」は「その人に聞けば分かる」を意味しない。
一方 `answer` は「実際に答えた」なので強い。

順位も効く（1位 0.865 / 2位 0.827 / 3位 0.635）。**ラベルは順位を一切見ていない。**

## 3. 置き換え案

```python
if "answer" not in sources:                     return "低"
if rank <= 2 and "project" not in sources:      return "高"
return "中"
```

| | 現行 | **置き換え案** |

| 中 | 0.900（n=30） | 0.758（n=91） |
| 低 | **一度も出ない** | 0.571（n=28） |
| 単調（高≧中≧低） | **いいえ** | **はい** |
| 高 − 低 | 測れない（低が無い） | **+0.402** 95%CI [+0.252, +0.536] |

### 選び方に下駄を履かせていないか

**この案は同じ156スロットの上で4つの候補から選んだ**ので、そのままでは出来すぎる。
**問題単位で半分に分け、学習半分でルールを選び、残り半分で測る**を200回繰り返した。

| | 検証半分での 高 − 低 |
|---|---|
| **選び直しを含めた手続き全体** | **中央 +0.380**、95%区間 [+0.115, +0.545]、**正の割合 0.995** |
| 順位だけ | 中央 +0.231 [+0.077, +0.386] |
| 証拠の種類だけ | 中央 +0.373 [+0.191, +0.500] |
| 順位＋証拠の種類 | 中央 +0.401 [+0.255, +0.533] |
| 現行 | **測れない**（「低」が出ないため） |

学習半分では 200回中 147回が「順位＋証拠の種類」を選んだ。**手続きごと検証しても効果は残る。**

## 4. 測っていないこと

* **gold トピックを渡した条件**である。C1 の実トピックでは候補の顔ぶれが変わるので、
  ラベルの精度も変わりうる（[llm_faithful.md](llm_faithful.md) §4.6 / #116）
* 候補は全社員（#87）。製品はいま C4 が返す候補だけを渡すので、**顔ぶれが違えば
  ラベルの精度も変わる**。#90 の閾値較正（PR #120）で経路が `person` に戻ったので
  3枠は出るようになったが、候補集合そのものは #87 が未対応である
* **この節の数字は埋め込みにも経路にも依存しない**（`rank(q, all_ids, …)` は
  `res` も `route` も読まない）。develop が Nemotron に変わっても、また
  C4 の重みが変わっても（#68 / PR #115）、ここは動かない
* n = 156スロット / 52問。閾値を細かく刻むには足りない。
  上の案が**閾値を持たない**（順位と種類の有無だけ）のは、そのためでもある
* 「低」を出すようになると**画面に「低」が出る**。UI 側の扱いを決める必要がある

## 5. 再現

```bash
python scripts/research_e2e.py --task misrec --pgdir <pgdata> \
    --out docs/benchmarks/ablation/misrecommendation.json
```

（`rank` / `topic_fit` / `evidence_count` / `evidence_sources` / `margin_to_next` / `hit`）。
**件数は `n_slots`**（旧版は `slots` が件数だった）。
