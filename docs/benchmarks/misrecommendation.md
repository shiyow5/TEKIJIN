# 誤推薦の質（Issue #107）

> **確信度ラベルの続き**: 「高」が「中」より当たらない件は
> [confidence.md](confidence.md)（#110）で素性まで掘ってある。
> `topic_fit` と証拠数は**問題をまたぐと** AUC 0.5 前後になる。ただし**同じ問題の3枠の中では
> 0.66〜0.68 で効いている**ので、素性が悪いのではなく、絶対値に閾値を当てているのが問題。

本プロジェクトは「**誤推薦対策**」を柱にしている（根拠つきの推薦・確信度・棄却）。
しかし測ってきたのは Recall@3 / MRR / Top-1 だけで、
**外したときに「どのくらい外しているか」を一度も見ていなかった。**

実施 2026-08-23。実 DB・実埋め込み・実 C6（`ExpertiseScorer`）。
gold トピックを渡し、候補は全社員（[scorer.md](scorer.md) §3 / #87）。
測定時点では **#103 で候補が1名しか出ず、現状のままでは外し方を見られなかった**
（#103 は #120 で解消済み。今は現状のままでも候補10名が出る）。
再現: `python scripts/research_e2e.py --task misrec`（**GPU不要**）。

> ✅ **埋め込み・経路には依存しない。** #132 と #84 の再測定では、埋め込みを替えても
> 経路閾値を替えてもクエリ文面を変えても、出力 JSON が **4回連続でバイト単位一致**した。
> 候補を全社員にすると `rank(q, all_ids, …)` が `res` も `route` も読まないためである。
>
> ⚠️ **ただし #158 で数字が動いた。** 制約つきを5件→15件に増やし、該当10件の **gold を
> その拠点の人に絞った**ため。gold が1〜2名になった問題では3枠のうち当てられる枠が減る。

## 1. 結論: 証拠ゼロの推薦は1件も無い

上位3枠 × 採点対象52件 = **156スロット**の内訳。

| 分類 | 件数 | 割合 |
|---|---|---|
| 正解 | 105 | 67.3% |
| **誤り: gold と同じ部署（そのトピックの証拠あり）** | **40** | **25.6%** |
| 誤り: gold と同じ拠点（部署は違う。証拠あり） | 5 | 3.2% |
| 誤り: 部署も拠点も違う（証拠あり） | 6 | 3.8% |
| **誤り: そのトピックの証拠ゼロ** | **0** | **0.0%** |

**「知らない人を自信満々に出す」形の誤推薦は起きていない。**
外した51スロットのうち **45件（88.2%）は gold と同じ部署か同じ拠点**で、
いずれもそのトピックの証拠（資格・スキル・案件・回答のいずれか）を持っている。

取り次ぎ先としては妥当な範囲に収まっている、と言ってよい。
C6 が「証拠から再計算する」設計になっている（保存済みの重みを信じない）ことが効いている。

> ここで言う「証拠」は `collect_topic_evidence` が返すもの。
> **gold の作り方（projects + daily_reports）とは別経路の証拠も含む**ので、
> 「証拠ゼロが0件」は gold をなぞった結果ではない。

## 2. 見つかった不具合: 確信度ラベルが逆転している

| ラベル | スロット数 | そのうち正解 |
|---|---|---|
| **高** | 126 | **64.3%** |
| **中** | 30 | **80.0%** |
| 低 | 0 | — |

**「高」のほうが「中」より当たらない。** ブートストラップでも支持される。

```
中 − 高 = +0.157   95%CI [+0.033, +0.290]   P(中>高) = 0.993   ← 問題単位の再標本化（20000回・seed 42）
中 − 高 = +0.157   95%CI [-0.017, +0.319]   P(中>高) = 0.961   ← スロット単位（参考）
```

> ⚠️ **引用するなら問題単位のほう。** 同じ問題の3枠は独立ではないので、スロット単位で振るのは
> 単位の取り違えである。
> **#158 前はスロット単位のほうが狭く出ていた（[+0.014,+0.278]）が、いまは逆に広い。**
> どちらに転ぶかはデータ次第なので、「スロット単位は必ず狭くなる」とは書けない。
> **単位が正しいから問題単位を使う**のであって、区間の広狭が理由ではない。

`confidence_label(edge_weight, evidence_count)` は
`edge_weight >= 0.7 かつ evidence_count >= 3` で「高」を出す。
実測では **`edge_weight >= 0.7` は1件も仕事をしておらず、「高」⟺「証拠が3件以上」**（126件 = 126件）。
一方 2段目の `edge_weight >= 0.4` は効いていて、**「低」が一度も出ない原因はこちら**である
（証拠1件の15スロットを全部「中」に拾っている）。

> ⚠️ **「回答を量産している人が高になりやすい」という当初の説明は取り下げた。**
> 素性まで掘ると、`answer`（過去に答えている）が**最も差の大きい証拠**だった（あり 0.820 / なし 0.571）。
> ただし `answer` の有無が問題内で割れているのは52問中7問しかないので、
> **これを「回答実績のある人は当たる」と人単位で読んではいけない**（大半は
> 「そのトピックに過去回答があるか」を見ている）。当たり外れを支配しているのは証拠の量ではなく、
> **その問題の gold 人数（＝難しさ）**である。詳細は [confidence.md](confidence.md)。

UI（#37 結果画面）はこのラベルを出しているので、**現状は「高」が誤誘導になっている**。

「低」が一度も出ないのも問題で、**3段階のうち2段階しか使われていない**。

## 3. 限界

1. **gold トピックを渡している。** 実際は C1 が推定するので、トピックを外した場合の
   誤推薦はここに含まれていない。[ablation.md](ablation.md) §4 のとおりトピック的中は 0.821 なので、
   **実運用の誤推薦率はここより高くなる**
2. **「同じ部署なら妥当」は仮説**。合成データでは部署とトピックがほぼ一対一なので、
   実データでは同じ部署でも見当違いということが起こりうる
3. **確信度の n が偏っている**（高126 / 中30 / 低0）。低が出ない以上、
   「低いときに棄却する」運用はこのラベルでは成立しない（棄却は #70 の別段で行う）

個別値は `ablation/misrecommendation.json`。
