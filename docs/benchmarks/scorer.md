# C6 スコアラーの重みは効いているのか（Issue #85）

C6（#30）の線形重みと base_score は doc15 の設計値のまま、**一度も測っていなかった**。
また #65 / #80 の実験で使っていたのは **base_score の素の和**（飽和も recency も無し）なので、
「C6 の式そのものが素の和より良いのか」も未確認だった。

実施 2026-08-22。`tekijin.scorer` の純関数（`collect_topic_evidence` / `edge_weight` /
`saturate` / `recency` / `answer_quality` / `proximity` / `load`）を**そのまま import** して測っている。
評価は `eval_person.json` の56件、トピックは LLM(検索文脈つき) の分類、基準（Dense 集約）= 0.601。
再現: `python scripts/research_c6_weights.py --emb emb/emb_Nemotron-3-Embed-1B-BF16.npz`（**GPU不要**）。

```
score = 0.45·topic_fit + 0.15·recency + 0.20·answer_quality + 0.10·proximity − 0.20·load
```

## 1. 結論

| | 結果 |
|---|---|
| C6 の式は素の base_score 和より良いか | **良い**（0.771 vs 0.759） |
| 手で決めた重みは妥当か | **妥当。交差検証で上回る設定が見つからない**（-0.003） |
| `load` ペナルティは精度を犠牲にしているか | **していない。むしろ Top-1 を +0.054 上げている** |
| C4 で候補を絞ってから C6 に渡すべきか | **絞らないほうがよい**（-0.030） |

## 2. 式そのもの・各項のアブレーション（候補=全40名）

| 構成 | R@3 | Δ（基準比） | MRR | Top1 |
|---|---|---|---|---|
| 素の base_score 和（#65/#80 で使っていた形） | 0.759 | +0.158 | 0.818 | 0.768 |
| **C6 の完全な式（既定重み）** | **0.771** | **+0.170** [+0.080,+0.259] | 0.818 | 0.768 |
| recency を 0 に | 0.759 | +0.158 | 0.800 | 0.732 |
| answer_quality を 0 に | 0.765 | +0.164 | 0.818 | 0.768 |
| proximity を 0 に | 0.771 | +0.170 | 0.818 | 0.768 |
| load を 0 に | 0.771 | +0.170 | **0.792** | **0.714** |
| topic_fit のみ（他を全部 0） | 0.759 | +0.158 | 0.818 | 0.768 |

**読み取れること。**

1. **式の追加分は効いている**が、幅は小さい（+0.012）。**大半は `topic_fit` が説明している**
2. **`recency` が唯一 R@3 を動かす追加項**（外すと -0.012、Top1 -0.036）。
   「最近その分野をやった人」を上げるのは実際に当たっている
3. **`load` ペナルティは精度を払っていない。** 外すと **Top1 が 0.768 → 0.714 に落ちる**。
   負荷分散のための項が、結果的に「回答を量産している人」の水増しを抑えている。
   **負荷分散と精度はこの設計ではトレードオフになっていない**
4. `proximity` は動かない。評価セットに `asker_id` が無く company-wide 固定になるため。**測れていない**（§4 で別途）

## 3. 候補集合 — C4 で絞ると落ちる

製品は C4（検索）で候補を出し、C6 がそれを並べ替える。**この絞り込みが正解を落としている。**

| 候補集合 | R@3 | Δ（基準比） | MRR |
|---|---|---|---|
| **全40名を C6 に渡す** | **0.771** | +0.170 | 0.818 |
| C4 相当の上位20名 | 0.741 | +0.140 | 0.793 |
| C4 相当の上位40名 | 0.741 | +0.140 | 0.793 |
| C4 相当の上位10名 | 0.729 | +0.128 | 0.795 |

上位40名にしても 0.741 で頭打ちなので、**「何名に絞るか」ではなく「C4 が拾える人の集合」の問題**。
Dense 検索の上位チャンクに現れない人は、証拠を持っていても候補に入らない。

**社員40名の規模なら、C4 を候補生成に使わず全社員を C6 でスコアするほうがよい。**
1件あたりの追加コストは数ミリ秒（C6 は LLM を使わない決定的な計算）。
数千人規模になったら、C4 を「候補を削る」ためではなく「トピックを当てる」ために使い、
候補は person_topic_edges 側から引くのが筋。

## 4. 拠点制約を `asker_branch` として渡す

| 構成 | 制約つき5件 | 全体 | Δ（基準比） |
|---|---|---|---|
| 渡さない（現状） | 0.700 | 0.771 | +0.170 |
| **渡す（proximity=0.10 のまま）** | **0.900** | **0.789** | +0.187 [+0.092,+0.283] |
| 渡す（proximity=0.40 に上げる） | 0.900 | 0.789 | +0.187 |

**重みを上げても変わらない**（0.10 で既に順位が決まっている）。
ただし [robustness.md](robustness.md) §3 の「拠点で絞る／加点する」は 1.000 だったので、
**proximity 項では取りきれない**。明示された制約は加点ではなく条件として扱うべき（#83）。

## 5. 重みのグリッド探索（5分割交差検証）

54通り（topic_fit 3 × recency 3 × answer_quality 3 × load 2）を、
**学習 fold で選んで検証 fold で測る**形で回した。

- 既定重みの全件スコア: **0.771**
- 交差検証でのスコア: **0.768**（既定との差 **-0.003**）
- 全 fold が同じ設定を選んだ（`answer_quality=0.0, load=0.0`）が、**それでも既定を上回らない**

**手で決めた重みを触る理由が無い。** 56件では ±0.09 未満を分離できないので、
「最適である」ではなく「**この評価セットでは既定より良い設定を見つけられない**」と読むこと。

## 6. 限界

- `asker_id` が評価セットに無いので **`proximity` はまともに測れていない**。
  §4 は `constraint` を代用したもので、5件しかない
- `recommendations` テーブルは実行時のものなので fixtures に無い。**`load` は直近7日の回答数のみ**で、
  推薦回数ぶんが入っていない。実運用では load はもっと大きく効く
- `ExpertiseScorer` 本体（Repository 依存）は呼んでいない。**式・重み・base_score・飽和・減衰は
  製品と同じ純関数を import している**が、DTO の組み立ては別実装

個別値は `ablation/c6_weights.json`。
