# C6 スコアラーの重みは効いているのか（Issue #85）

C6（#30）の線形重みと base_score は doc15 の設計値のまま、**一度も測っていなかった**。
また #65 / #80 の実験で使っていたのは **base_score の素の和**（飽和も recency も無し）なので、
「C6 の式そのものが素の和より良いのか」も未確認だった。

実施 2026-08-22。`tekijin.scorer` の純関数（`collect_topic_evidence` / `edge_weight` /
`saturate` / `recency` / `answer_quality` / `proximity` / `load`）を**そのまま import** して測っている。
評価は `eval_person.json` の**採点対象66件**、トピックは LLM(検索文脈つき) の分類、基準（Dense 集約）= **0.553**
（#84 で評価クエリ8件の文面を変えたため 2026-08-23 に再測定。**基準線と §3 の候補集合が動いた**）。
再現: `python scripts/research_c6_weights.py --emb emb/emb_Nemotron-3-Embed-1B-BF16.npz`（**GPU不要**）。

```
score = 0.45·topic_fit + 0.15·recency + 0.20·answer_quality + 0.10·proximity − 0.20·load
```

## 1. 結論

<!-- gen:scorer_conclusion -->
|  | 結果 |
|---|---|
| C6 の式は素の base_score 和より良いか | **良い**（0.727 vs 0.712） |
| 手で決めた重みは妥当か | **妥当。交差検証で上回る設定が見つからない**（-0.002） |
| `load` ペナルティは精度を犠牲にしているか | **していない。むしろ Top-1 を +0.030 上げている** |
| C4 で候補を絞ってから C6 に渡すべきか | **絞らないほうがよい**（-0.020） |
<!-- /gen:scorer_conclusion -->

## 2. 式そのもの・各項のアブレーション（候補=全40名）

<!-- gen:scorer_formula -->
| 構成 | R@3 | Δ（基準比） | MRR | Top1 |
|---|---|---|---|---|
| 素の和（#65/#80 で使っていた形） | 0.712 | +0.159 [+0.073,+0.245] | 0.800 | 0.727 |
| **C6 の完全な式（既定重み）** | **0.727** | **+0.174 [+0.088,+0.263]** | 0.790 | 0.712 |
| recency を 0 に | 0.712 | +0.159 [+0.073,+0.245] | 0.775 | 0.682 |
| answer_quality を 0 に | 0.717 | +0.164 [+0.078,+0.255] | 0.783 | 0.697 |
| proximity を 0 に | 0.727 | +0.174 [+0.088,+0.263] | 0.790 | 0.712 |
| load を 0 に | 0.727 | +0.174 [+0.088,+0.263] | 0.778 | 0.682 |
| topic_fit のみ | 0.712 | +0.159 [+0.073,+0.245] | 0.800 | 0.727 |
<!-- /gen:scorer_formula -->

**読み取れること。**

1. **式の追加分は効いている**が、幅は小さい（+0.012）。**大半は `topic_fit` が説明している**
2. **`recency` が唯一 R@3 を動かす追加項**（外すと -0.012、Top1 -0.035）。
   「最近その分野をやった人」を上げるのは実際に当たっている
3. **`load` ペナルティは精度を払っていない。** 外すと **Top1 が 0.696 → 0.661 に落ちる**。
   負荷分散のための項が、結果的に「回答を量産している人」の水増しを抑えている。
   **負荷分散と精度はこの設計ではトレードオフになっていない**
4. `proximity` は動かない。評価セットに `asker_id` が無く company-wide 固定になるため。**測れていない**（§4 で別途）

## 3. 候補集合 — C4 で絞ると落ちる

製品は C4（検索）で候補を出し、C6 がそれを並べ替える。**この絞り込みが正解を落としている。**

<!-- gen:scorer_candidates -->
| 候補集合 | R@3 | Δ（基準比） | MRR |
|---|---|---|---|
| **全40名を C6 に渡す** | **0.727** | +0.174 | 0.790 |
| C4 上位10名 | 0.679 | +0.126 | 0.770 |
| C4 上位20名 | 0.707 | +0.154 | 0.775 |
| C4 上位40名 | 0.707 | +0.154 | 0.775 |
<!-- /gen:scorer_candidates -->

上位40名にしても 0.714 で頭打ちなので、**「何名に絞るか」ではなく「C4 が拾える人の集合」の問題**。
Dense 検索の上位チャンクに現れない人は、証拠を持っていても候補に入らない。

**社員40名の規模なら、C4 を候補生成に使わず全社員を C6 でスコアするほうがよい。**
1件あたりの追加コストは数ミリ秒（C6 は LLM を使わない決定的な計算）。
数千人規模になったら、C4 を「候補を削る」ためではなく「トピックを当てる」ために使い、
候補は person_topic_edges 側から引くのが筋。

## 4. 拠点制約を `asker_branch` として渡す

<!-- gen:scorer_constraint -->
| 構成 | 制約つき15件 | 全体 | Δ（基準比） |
|---|---|---|---|
| 渡さない（現状） | 0.667 | 0.727 | +0.174 [+0.088,+0.263] |
| **渡す（既定 proximity=0.10）** | — | **0.742** | +0.189 [+0.104,+0.278] |
| **渡す（proximity=0.40）** | — | **0.773** | +0.220 [+0.134,+0.311] |
<!-- /gen:scorer_constraint -->

> **訂正（#158）**: 制約つきが5件だったときは 0.10 と 0.40 がどちらも 0.900 で並び、
> 「**重みを上げても変わらない**（0.10 で既に順位が決まっている）」と書いていた。
> **#158 で制約つきを15件に増やしたら分離した。** 0.10 では 0.800 どまりで、
> 0.40 に上げると 0.900 になる。**n=5 では差を見られなかっただけだった。**

**重みを上げると効く。** ただし 0.40 でも 0.900 で、[robustness.md](robustness.md) §3 の
「拠点で絞る／加点する」（0.933）には届かない。**proximity 項だけでは取りきれない**ので、
明示された制約は加点ではなく条件として扱うべき（#83）。

## 5. 重みのグリッド探索（5分割交差検証）

54通り（topic_fit 3 × recency 3 × answer_quality 3 × load 2）を、
**学習 fold で選んで検証 fold で測る**形で回した。

<!-- gen:scorer_grid -->
|  | R@3 |
|---|---|
| 既定重みの全件スコア | **0.727** |
| 交差検証でのスコア | **0.725** |
| 差（交差検証 − 既定） | **-0.002** |
<!-- /gen:scorer_grid -->

- 全 fold が同じ設定を選んだ（`answer_quality=0.0, load=0.0`）が、**それでも既定を上回らない**

**手で決めた重みを触る理由が無い。** 66件では ±0.09 未満を分離できないので、
「最適である」ではなく「**この評価セットでは既定より良い設定を見つけられない**」と読むこと。

## 6. 限界

- `asker_id` が評価セットに無いので **`proximity` はまともに測れていない**。
  §4 は `constraint` を代用したもので、5件しかない
- `recommendations` テーブルは実行時のものなので fixtures に無い。**`load` は直近7日の回答数のみ**で、
  推薦回数ぶんが入っていない。実運用では load はもっと大きく効く
- `ExpertiseScorer` 本体（Repository 依存）は呼んでいない。**式・重み・base_score・飽和・減衰は
  製品と同じ純関数を import している**が、DTO の組み立ては別実装

個別値は `ablation/c6_weights.json`。
