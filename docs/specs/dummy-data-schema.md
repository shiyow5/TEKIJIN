# ダミーデータ仕様書（社員マスタ・チャット履歴・案件履歴・日報）

- ステータス: ドラフト（レビュー依頼中）
- 作成日: 2026-08-21
- 対象: `employees.json` / `chat_history_dummy.json` / `case_history_dummy.json` / `daily_report_dummy.json`
- 関連: `eval_queries.json`（本ドキュメントの対象外。9章「既知の制約・今後の課題」を参照）

## 1. 目的・背景

TEKIJIN（社内の「これ誰に聞けばいいんだろう」をAIが解決するレコメンドプロダクト）の開発にあたり、実データが存在しない段階でアルゴリズムの設計・精度検証を行うために作成した仮想（ダミー）データ一式の仕様をまとめる。実在の人物・企業・案件とは一切関係がない。

## 2. 全体設計方針

各データセットは、それぞれの業務領域で実際に管理されていそうな項目（社員台帳・チャットログ・案件管理・日報）を独立してモデル化している。

初期検討時は、全ファイル共通の「トピック（業務分野）×専門家」マッピングを軸にデータを生成し、チャット・案件・日報のいずれからも「この人はこの分野に詳しい」という一貫したシグナルを再現する設計だった。その後、より実務データに近い形にするため各ファイルのスキーマを個別に見直し、共通トピック体系への依存を解消した。現在はファイル間の対応関係を `employees.json` の `name` / `department` のみで担保している（詳細は7章「データ間のリレーション」を参照）。

## 3. `employees.json` — 社員マスタ

社員40名の基本情報（所属・連絡先・役職・入社日・部署異動履歴）を一覧化したマスタデータ。

### スキーマ

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | number | 社員ID（連番） |
| `name` | string | 氏名 |
| `department` | string | 現在の所属部署 |
| `email` | string | メールアドレス |
| `position` | string | 役職（`部長` / `課長` / `主任` / `一般社員`） |
| `hire_date` | string (YYYY-MM-DD) | 入社日 |
| `department_history` | object[] | 部署異動の履歴。各要素は `{ department, start_date, end_date }`。現所属の `end_date` は `null` |

### サンプル

```json
{
  "id": 2,
  "name": "佐藤 花子",
  "department": "営業部",
  "email": "sato.hanako@sample-tekijin.co.jp",
  "position": "課長",
  "hire_date": "2016-04-01",
  "department_history": [
    { "department": "マーケティング部", "start_date": "2016-04-01", "end_date": "2020-03-31" },
    { "department": "営業部", "start_date": "2020-04-01", "end_date": null }
  ]
}
```

### 件数・分布

- 全40名。部署は営業部・マーケティング部・情報システム部・人事部・経理部・総務部・開発部・カスタマーサポート部・購買部・広報部の10部署に各4名ずつ均等配置。
- 役職は部長・課長・主任・一般社員が各部署1名ずつ（全体で各10名）。
- 40名中8名（id 2, 9, 14, 18, 24, 28, 33, 36）は過去に部署異動を経験しており、`department_history` に2件以上のエントリを持つ。残りは入社時から異動なし（1件のみ）。

## 4. `chat_history_dummy.json` — チャット履歴

社内チャットの発言ログを模した仮想データ。全2000件。

### スキーマ

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | number | メッセージID（連番、`timestamp` 昇順で振り直し済み） |
| `speaker` | string | 発言者（`employees.json` の `name` と対応） |
| `channel` | string | チャンネル名（`general` / `営業部-連絡` / `開発部-連絡` / `雑談` / `IT問い合わせ` / `経理・総務`） |
| `timestamp` | string (ISO8601) | 発言日時（`YYYY-MM-DDTHH:MM:SS`） |
| `message` | string | 発言内容 |

### サンプル

```json
{
  "id": 7,
  "speaker": "高橋 美咲",
  "channel": "IT問い合わせ",
  "timestamp": "2026-04-01T11:19:22",
  "message": "メールが届かないトラブルが発生しています。"
}
```

### 生成ロジックの要点

- チャンネルは `general` 30% / `雑談` 20% / `営業部-連絡` 15% / `開発部-連絡` 15% / `IT問い合わせ` 10% / `経理・総務` 10%の重み付けで選出。
- `speaker` はチャンネルに応じて偏りを持たせている。`営業部-連絡` は営業部社員が8割、`開発部-連絡` は開発部社員が8割、`IT問い合わせ` は情報システム部社員が4割（残りは他部署からの問い合わせ）、`経理・総務` は経理部・総務部社員が4割（残りは他部署からの問い合わせ）。`general` / `雑談` は全社員から均等に選出。
- `message` はチャンネルごとに用意した文面候補から選出（業務連絡・問い合わせ・雑談などチャンネルの性質に沿った内容）。
- 発言日時は2026年4月1日〜8月19日の平日のみ、業務時間帯に偏らせて生成（7割が9〜15時台、残りは8時台・16〜19時台）。

## 5. `case_history_dummy.json` — 案件履歴

営業・SI案件の履歴を模した仮想データ。全120件。

### スキーマ

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | number | 案件ID（連番、`start_date` 昇順で振り直し済み） |
| `title` | string | 案件名 |
| `status` | string | `完了` / `進行中` / `失注` / `保留` |
| `department` | string | 主担当者の所属部署（営業部・開発部・カスタマーサポート部・マーケティング部のいずれか） |
| `name` | string | 主担当者名（`employees.json` の `name` と対応） |
| `customer_company` | string | 顧客の企業名（架空） |
| `industry` | string | 顧客の業界 |
| `company_size` | string | 顧客企業の規模（`大企業` / `中小企業`） |
| `product` | string | 提供プロダクト・サービス名 |
| `issue` | string | 顧客の課題 |
| `start_date` | string (YYYY-MM-DD) | 案件開始日 |
| `end_date` | string (YYYY-MM-DD) \| null | 完了・クローズ日。`進行中` / `保留` の場合は `null` |

### サンプル

```json
{
  "id": 1,
  "title": "株式会社ノーザンメディカル様 Web広告の費用対効果低下についての商談",
  "status": "失注",
  "department": "マーケティング部",
  "name": "伊藤 健太",
  "customer_company": "株式会社ノーザンメディカル",
  "industry": "医療・福祉",
  "company_size": "大企業",
  "product": "Webマーケティング支援",
  "issue": "Web広告の費用対効果低下",
  "start_date": "2026-04-03",
  "end_date": "2026-06-08"
}
```

### 生成ロジックの要点

- `department` は営業部40% / 開発部25% / カスタマーサポート部20% / マーケティング部15%の重み付けで選出し、`name` はその部署に所属する4名からランダムに選出（案件は顧客接点を持つ4部署のみが担当する想定）。
- `product` は `department` ごとに用意した候補リストから選出し、`issue` はその `product` に紐づく課題候補から選出（内容の一貫性を担保）。
- `company_size` は中小企業70% / 大企業30%の重み付け。`customer_company` は65社のプールからランダム選出のため、同一顧客が複数案件を持つケースもある。
- 案件期間は7〜90日でランダムに設定。開始日は2026年4月1日〜8月19日の範囲でランダム。スナップショット日（2026年8月19日）時点で終了している案件は `完了`（75%）/ `失注`（25%）、未終了の案件は `進行中`（80%）/ `保留`（20%）とし、後者は `end_date` を `null` とする。

### 未実装（拡張予定）の項目

初回検討時に候補に挙がったが、今回は基本項目のみで実装したもの。今後必要に応じて追加する。

- 金額規模、優先度、成果・受失注理由、使用技術タグ、副担当者、案件概要（自由記述）、関連ドキュメントリンク

## 6. `daily_report_dummy.json` — 日報

社員が日々提出する業務日報を模した仮想データ。全3070件。

### スキーマ

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | number | 日報ID（連番、`reported_at` 昇順で振り直し済み） |
| `name` | string | 提出者（`employees.json` の `name` と対応） |
| `department` | string | 提出者の所属部署 |
| `content` | string | 業務内容・課題（自由記述。レコメンドの類似検索で利用する主要テキスト） |
| `reported_at` | string (ISO8601) | 日報を書いた日時（対象業務日の夕方、平日のみ） |
| `registered_at` | string (ISO8601) | システムにデータを登録した日時（`reported_at` 以降） |

### サンプル

```json
{
  "id": 1,
  "name": "中島 健一",
  "department": "情報システム部",
  "content": "サーバーの定期メンテナンスを実施した。",
  "reported_at": "2026-04-01T17:03:15",
  "registered_at": "2026-04-01T17:06:20"
}
```

### 生成ロジックの要点

- 全社員が毎日提出するわけではなく、平日ごとに1人あたり提出率75%でランダムに提出有無を決定（40名 × 平日101日 × 75% ≒ 3030件が期待値、実際の生成結果は3070件）。
- `content` は提出者の所属部署ごとに用意した業務内容候補（85%）と、部署によらない一般的な業務内容候補（15%：定例会議参加や資料整理など）から選出。
- `reported_at` は対象業務日の17〜19時台（終業前後に日報を書く想定）。
- `registered_at` は90%が `reported_at` の1〜20分後（その場で登録）、残り10%は翌営業日の朝8〜9時台（翌日入力による登録遅延）。いずれも `registered_at` が `reported_at` を下回ることはない。

### 未実装（拡張予定）の項目

- 明日の予定、工数（時間）、訪問先/商談先、上長コメント、関連案件（`case_history_dummy.json` との紐付け）

## 7. データ間のリレーション

```
employees.json (name)
   ├─ chat_history_dummy.json.speaker
   ├─ case_history_dummy.json.name
   └─ daily_report_dummy.json.name
```

- 上記3ファイルの `department` は、参照時点の `employees.json` の `department`（現所属）と一致するよう生成している。
- `case_history_dummy.json` と `daily_report_dummy.json` の間に案件ID等での直接的な参照関係は現状ない（`daily_report_dummy.json` の `related_case_id` は今回のスキーマ刷新で廃止した）。
- 各ファイルが共通で参照していた「トピック（業務分野）」の体系は廃止済み。`eval_queries.json` のみ旧体系の `topic` / `correct_experts` を保持しているが、本ドキュメントの対象外（9章を参照）。

## 8. 生成方法・再現性

- 各ファイルは個別の Python スクリプトで生成（いずれも `random.seed(42)` により再現可能）。生成スクリプトは本リポジトリには未格納（ローカル作業フォルダの scratchpad 内）。リポジトリに取り込む場合は `scripts/` 配下への配置を検討する。
- 対象期間：2026年4月1日〜2026年8月19日（平日のみ）。
- 件数：`employees.json` 40件 / `chat_history_dummy.json` 2000件 / `case_history_dummy.json` 120件 / `daily_report_dummy.json` 3070件。

## 9. 既知の制約・今後の課題

- メッセージ・日報内容・案件タイトルはいずれもテンプレート文の組み合わせで生成しているため、実際のチャットや文章に比べて表現の多様性・自然さは限定的。精度検証の第一段階（アルゴリズムのロジック検証）を主目的としたデータであり、自然言語表現の頑健性評価には別途より自然な文面のデータが必要。
- 企業名・氏名はすべて架空。実在の組織・個人とは一切関係がない。
- `eval_queries.json`（レコメンド精度評価用の正解データセット）は、旧スキーマ（`employees.json` の `expert_topics` および各ファイルの `topic` / `category`）を前提に作成されたものであり、2026-08-21 のスキーマ刷新には追随できていない。現状は `employees.json` にも他3ファイルにもトピック体系が存在しないため、`eval_queries.json` の `topic` / `correct_experts` は突合先を失っている。評価データセットとして使い続ける場合は、別途改訂方針の検討が必要。
